# Architecture

DealGuard runs as a Next.js frontend and FastAPI backend. SQLAlchemy stores tenants, customers, products, actors, account/password hashes, server-side sessions, policy versions with applicability scopes, runs, approval requests, policy drafts and quote drafts in the configured database. SQLite remains the local default; PostgreSQL 18 is supported through psycopg 3. Alembic migrations add tenant ownership/authentication tables, backfill existing rows to `harborlight-demo`, replace the actor-only idempotency uniqueness with a tenant-scoped key, and split product identity into an internal UUID and a tenant-local SKU. The public product `id` remains a compatibility alias for SKU; quote and approval rows retain `product_id` as the SKU snapshot and reference the product UUID through `product_key`.

The LangGraph workflow parses an inquiry, then optionally lets a bounded Action Planner select tenant-scoped read-only customer, product, inventory, or policy-evidence tools. Product search terms must come from the inquiry; no planner tool can write data. The workflow loads trusted customer/product facts, derives policy scope on the server, and filters eligible policies by tenant, customer tier, action, effective dates, and scope before retrieval. BM25 ranks exact clauses; when a local Qwen3 model is configured, Dense retrieval joins the clause ranking and multiple eligible policies are selected only when BM25 and Dense agree. Citations remain exact source substrings with stored line references and source hashes. A deterministic Guard independently checks ownership, scope, inventory, discount, and approval rules before any quote write. Ambiguous policies fail closed. The manager endpoint revalidates the active policy and business facts before creating a quote in the same database transaction.

Policy Diff is read-only and always scopes customer, product, and policy lookups to the active tenant. Sales is bound to its assigned customer; managers and administrators can choose a tenant customer for simulation. Manager catalogue reads are limited to the customer/product data needed by that comparison. Duplicate product lines keep their individual discount terms but inventory is checked against their aggregate requested quantity, both when a quote is evaluated and again when a manager approves it. Managers can open tenant run details with customer message and nonessential trace fields redacted; administrators retain full run detail access. Policy draft activation writes the new version, active-version switch, draft state, and audit event in one transaction. SQLite runtime and test connections both enable foreign-key enforcement.

Migration `0014_product_sku` moves legacy product IDs into `sku`, assigns UUID primary keys, adds `UNIQUE(tenant_id, sku)`, and remaps quote/approval foreign keys through `product_key` without changing their historical SKU snapshots. Existing API clients may continue sending `id`; new clients can send `sku`. A downgrade restores SKU as the global primary key and is rejected if duplicate SKUs exist across workspaces, because that state cannot be represented by the old schema. Back up the database before production migrations and use the migration's downgrade guard only as a safety boundary, not as a substitute for backup/restore.

Policy uploads accept UTF-8 Markdown/text as source evidence only. Administrators separately confirm structured fields before activation. Diff evaluates the same inquiry against two registered versions without writing a quote or changing activation. Run traces record stage and end-to-end duration. Token usage is persisted only when returned by a configured provider; Demo usage stays unknown.

The CSV endpoint derives values from the stored quote and applies the same owner/Admin access rule as quote reads. Every business query is tenant-scoped, and owner/admin checks remain in force within that tenant. In development, `X-Demo-Actor` can select fixed backend actors. In production, that header is ignored: login checks a PBKDF2-SHA256 password hash, issues a random opaque 12-hour HttpOnly/SameSite=Strict cookie, and stores only its SHA-256 hash in the database. Role and tenant are read from the server-side actor record. There is no client-provided role or tenant input. This is a first-party self-hosted authentication baseline; account recovery, MFA, external IdP, CSRF strategy for cross-site deployment, and enterprise lifecycle management remain out of scope.

Inquiry creation optionally accepts an `Idempotency-Key`. Its SHA-256 payload fingerprint and key are stored with the Run, uniquely scoped to the Demo actor. Terminal responses replay from the persisted Run record; a key reused with another inquiry is rejected. Quote/approval creation and the terminal Run result commit together after workflow execution, so a failed workflow cannot leave an unpaired quote. A 60-second lease and monotonically increasing attempt number allow a retry with the original key to reclaim an interrupted Run; the final write is fenced by that attempt number so an older execution cannot commit. Recovery reruns inquiry parsing and can call a configured model again. Manager decisions use a conditional `PENDING` state update; concurrent approvals cannot create duplicate drafts. Requests without an idempotency key remain supported but cannot be replayed or recovered automatically.

Policy Change Impact simulation is administrator-only. Frozen Intent Replay uses trusted customer, product, inventory, actor, and policy snapshots saved with new Run records and calls the same Guard without writes. End-to-End Replay reruns the workflow against current business data and a transient candidate policy inside a database savepoint that is rolled back, so simulated quote inserts do not persist. Older Runs without snapshots are skipped in frozen mode.

The demo reset clears business records while retaining tenants, built-in actors and authentication accounts. See [`计划.md`](../计划.md) for the completed scope and P2 sequence.
